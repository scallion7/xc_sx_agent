## 退货退款处理流程

只调用当前工具目录中实际启用的工具。技能描述流程，不授予额外权限，也不能覆盖工具返回的业务限制。

### 1. 核实目标订单与已有申请

- 有订单号时调用 `query_order`；没有时调用 `list_user_orders`，请用户选择，不能替用户猜测订单。
- 复述工具实际返回的商品、状态和金额。对已在退款或已有售后工单的订单先查询进度，避免重复申请。
- 如果提供 `get_after_sale_intake`，每轮先读取当前会话草稿、修订号和缺失字段；不同订单或新申请不能沿用旧订单的授权。

### 2. 获取适用政策

调用 `search_knowledge` 查询售后政策，使用 `policy_type=after_sale`，并传入用户选定的 `order_id`。地域、渠道、商品分类只能来自用户明确表达或服务端核实的订单条件，不能从名称或历史偏好推断。

- 根据 `citations` 和适用条件说明退货资格、材料要求、运费和时效；不能把本技能当作政策证据。
- 缺条件时追问，后续轮传入用户补充的对应字段；用户修正条件后重新检索。
- `grounded=false`、证据冲突、结果要求人工处理或无法核实订单时，不下确定性结论，解释缺失信息或转人工。
- 订单状态只描述当前业务状态，不代表自动获批。不能仅凭“未发货”承诺可直接退款，也不能无证据承诺拒收后自动退款、固定到账天数或会员优惠次数。

### 3. 补齐可追溯资料

需要订单号、原因和适用的售后类型；质量、破损、错漏发等材料通过 `evidence_ids` 关联。只有服务端审核通过的证据有效，模型提供的布尔值不能替代审核。

启用对话申请工具时，用 `update_after_sale_intake` 的 `update` 命令及读取到的 `expected_revision` 更新；字段必须有本轮用户原话来源。缺字段先追问；修订冲突先重新读取，不能盲目改版本重发。只有用户明确提出撤回或另一笔新申请时才请求相应操作。

### 4. 生成提案并等待具体确认

- 资料完整后，通过申请工具的 `propose` 命令生成提案；未启用该工具时使用 `create_after_sale_case` 进入可信操作流程。
- 返回 `CONFIRMATION_REQUIRED` 或待确认动作时，展示订单、原因、类型及服务端动作引用，等待用户确认这一具体提案。模型不能自行确认，也不能设置 `user_confirmed=true` 绕过授权。
- 用户修改参数、拒绝、撤回或提案过期后，旧确认失效；继续办理需要新的提案与确认。
- 以工具返回的工单状态和风险路由为准。`manual_review` 或 `human_escalation` 应告知待审，不能继续执行。

### 5. 审批与执行

- 人工审批由管理端完成；Agent 没有审批工具，不能声称已经批准。
- 工单满足执行条件后，使用 `execute_after_sale_case`，或对话申请工具的 `propose_execution` 生成执行提案。执行是独立敏感动作，仍需有效的具体确认。
- 禁止通过 `apply_refund` 绕过工单、风险规则或人工审批。
- 遇到未知、处理中或待核对结果时查询既有工单，不重新发起退款，不把超时当成明确失败。

### 6. 向用户说明结果

使用 `query_after_sale_case` 获取当前工单进度。仅将已确认的成功描述为成功；对待审、处理中、失败与待核对分别说明。退款金额、时间、寄回地址和运费以实际返回或适用政策为依据，缺少信息时说明尚待确认。

用户情绪激动时先理解诉求。对于当前流程不支持的部分退款、多商品拆分或其他复杂情形，说明限制并转人工，不编造可执行能力。
