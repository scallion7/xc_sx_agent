# 第 24 期：工单并发唯一约束与业务幂等

第 23 期保证同一个 action 的确认只被领取一次，但两个会话可以各自产生有效
action，同时为同一订单创建工单。原实现先 `find_active_by_order()` 再 `save()`，
查询与写入之间存在竞态。本期把这个业务不变量落实到数据库和仓储原子操作中。

本期按当前开发范围交付工单创建、业务幂等及配套版本校验，使用现有 `user_id`
隔离。最初路线中的 tenant_id、外部身份映射和会话顺序治理不在本期交付中。

## 1. 业务规则

| 场景 | 当前行为 |
|---|---|
| 同一用户、同一订单的并发请求 | 最多存在一个活跃工单；竞争失败方回读已存在工单 |
| 相同创建幂等键、相同规范化参数 | 返回原关联工单的当前状态，跨重启仍有效 |
| 相同键、更换订单/原因/类型/证据 | 返回 `CASE_IDEMPOTENCY_CONFLICT`，不创建工单 |
| 不同键、同一订单已有活跃工单 | 复用已有工单，登记新键到该工单的关联，不修改其内容 |
| 原工单完成或拒绝，新键再次申请 | 活跃名额已释放，可以按当前业务校验创建新工单 |
| 原工单已结束，但重放旧键 | 仍返回原工单，不误建新的工单 |
| 工单处于 execution_failed | 仍占用活跃名额，需要处理现有失败工单 |
| 并发审批、旧版本回写 | 只有匹配当前 version 的写入成功；其他返回版本冲突 |

活跃定义为状态不属于 `completed`、`rejected`。未知状态也按活跃处理，避免放宽
唯一性。唯一范围是 `(user_id, order_id)`，不同用户的同号订单分别隔离。

创建响应新增：

```json
{
  "success": true,
  "created": false,
  "idempotent": true,
  "idempotency_scope": "active_order",
  "request_matches": false,
  "message": "返回已有关联工单的当前状态，未创建新工单，也未修改原工单内容",
  "case": {"case_id": "AS-...", "status": "approved", "version": 1}
}
```

`idempotency_scope` 为 `new`、`active_order` 或 `request_key`。`request_matches`
比较本次业务参数与返回工单当前保存的创建内容。为兼容已有行为，不同原因仍可
关联同一个活跃工单，但会明确标记不匹配；不能把 `success=true` 理解为已修改
原工单原因或创建了另一类售后。调用者应检查 `created` 和返回工单内容。

## 2. SQL：唯一约束与创建事务

新增部分唯一索引（SQLite / PostgreSQL）：

```sql
CREATE UNIQUE INDEX uq_after_sale_active_user_order
ON after_sale_cases(user_id, order_id)
WHERE status NOT IN ('completed', 'rejected');
```

索引保护所有数据库插入和状态更新，包括绕过 Service 的写入。工单 `version`
则由仓储采用条件更新实现，原子地执行 `WHERE case_id = ... AND version = ...`。
新工单版本为 1；历史工单迁移版本为 0，每次成功保存递增。所有权和订单号不可
通过 `save()` 修改，避免工单与幂等记录关联到另一个用户或订单。

新增 `after_sale_creation_requests`：

| 字段 | 作用 |
|---|---|
| user_id + idempotency_key | 联合主键，同一用户下创建请求的稳定身份 |
| request_hash | 订单、原因、推断后的售后类型、已核实举证标记和证据 ID 的 SHA-256 |
| case_id | 对应工单外键；多个请求键可指向同一个活跃工单 |
| created_at | 关联建立时间 |

参数规范化会移除订单/原因首尾空白，将 auto 转为具体类型，证据 ID 去重排序；
不修改原因内部文字。创建键最长 128 字符，不允许只含空白。

```text
可信确认 → 创建服务
  ├─ 已有请求键 → 校验 request_hash → 返回原工单当前状态
  └─ 新请求 → 查订单、评估风险 → repository.create_or_get
       └─ 一个事务：复核请求键 → 读取活跃工单
                      → 必要时插入工单 → 插入请求键关联 → 提交
            唯一冲突：整个事务回滚 → 新事务回读胜出者
```

原子提交避免“工单已经建好，但创建键没落库”的中间状态。不同订单竞争同一键时，
失败方刚插入的工单也会回滚，不留下孤立工单。仅识别活跃唯一索引和请求键主键
冲突作为可恢复竞争，其他数据库错误不会被伪装成幂等成功。竞争回读最多尝试
4 次，持续冲突返回 `CASE_CREATE_BUSY`。

创建阶段没有支付、退款等外部写操作；订单查询和风险评估在创建事务外完成，
不持有数据库锁等待模型或外部服务。幂等键重放直接读取账本，不重新调用订单
Provider 或重新评估风险；返回的是原业务请求的关联结果。

## 3. 与可信执行入口衔接

外部接口仍使用第 23 期的提案 → confirm → execute 流程。执行注册表向创建处理器
注入可信上下文，生成内部创建键 `action:{action_id}`。模型工具 Schema 不暴露
`idempotency_key` 或 `context`；模型尝试提交这些字段会被契约校验拒绝。

跨会话、不同 action 的相同订单请求通过活跃唯一约束收敛；重复调用同一个 action
仍优先由第 23 期 action 结果账本重放。内部开发调用 `AfterSaleService.create_case`
可显式传入稳定 `idempotency_key`；直接调用领域服务是可信应用代码能力，不是
另一个允许用户填 `user_confirmed=true` 的开放接口。

没有传入创建键的旧内部调用仍兼容，仅提供活跃工单去重；在终态后无键重试无法
识别是否为旧请求。需要跨终态重试保证的调用必须使用稳定创建键。

`EvidenceRecord` 的归属、审核和变更确认规则沿用第 23 期。创建工单现在保存
`evidence_ids`，参与业务请求摘要；这些 ID 不替代审核校验。

事件沿用统一总线：`after_sale.case.created`、`after_sale.case.reused`、
`after_sale.case.conflict`。创建/复用事件包含工单 ID、用户、订单、version、
幂等范围和参数匹配标记；重复请求不会再次追加 `case_created` 工单审计。

## 4. JSON 后端

JSON 仓储以稳定的 `.lock` 旁文件加进程锁，锁住完整的读取、判断和写入过程，
同时用进程内 RLock 协调线程。工单与创建键放在同一个 JSON 文档中，通过独立
临时文件、flush/fsync 和 `os.replace` 一次替换提交，避免两个文件之间部分成功。

读取兼容旧版 `version: 1` 工单文件；首次写入保存为 `version: 2`，增加
`creation_requests`。坏 JSON、重复 case_id 或重复活跃工单会报错，不会按空文件
覆盖。写入替换失败会保留旧文件，并清理临时文件。

该保证适用于所有写者都使用本仓储的本地文件系统；不保证 NFS、跨主机写入或
绕过锁直接编辑文件。它仅覆盖工单仓储，不表示其他 JSON 仓储也已具备进程锁。
POSIX 路径已实测；Windows msvcrt 分支尚未在本次本地验收中运行。

## 5. 迁移与部署

新增迁移 `20261023_0003`，前驱为第 23 期 `20261023_0002`。基线迁移中的旧工单
表改为显式历史定义，避免最新 metadata 把新字段/索引提前带入旧版本。

已有数据库应先暂停工单写入并备份，再执行：

```bash
python -m app.scripts.manage_migrations upgrade
python -m app.scripts.manage_migrations check
alembic check
```

上述升级路径适用于空库或已有 Alembic 版本记录的数据库。早期仅通过自动建表
生成、没有迁移版本标记的演示库，需要先核对实际 schema 并登记对应历史基线；
不要直接 `stamp head` 跳过迁移。保留数据时应先在备份副本完成该基线核对，
不能把“表已经存在”当成迁移已经执行。

升级在添加字段、索引、幂等表之前检测重复活跃工单。检测失败返回
`CASE_ACTIVE_DUPLICATES` 和最多 10 组用户/订单；保留旧迁移版本及原数据。可用
下面的只读查询定位，不自动合并、拒绝或删除涉及审批和退款的记录：

```sql
SELECT user_id, order_id, COUNT(*) AS count
FROM after_sale_cases
WHERE status NOT IN ('completed', 'rejected')
GROUP BY user_id, order_id
HAVING COUNT(*) > 1;
```

`DATABASE_AUTO_CREATE=true` 仅用于新库建表，不升级旧工单表。检测旧 schema 时，
应用在创建新表前报 `CASE_SCHEMA_UPGRADE_REQUIRED`；SQL 工单仓储也验证 version
字段、创建账本和活跃唯一索引，避免缺少约束却继续提供创建服务。

降级到 `20261023_0002` 保留工单主要业务字段及审计，但删除创建幂等表、唯一索引
和版本列，并移除 payload 中新加的 version/evidence_ids，供旧版模型读取。因此
降级会丢失本期幂等关联、版本计数和工单内证据 ID 副本；先备份，停止应用写入，
不能把降级当成在线业务回滚。第 23 期证据原表和 action 提案保留。JSON 文件没有
自动降级工具，需要恢复升级前的备份。

## 7. 实现入口与工程边界

| 文件 | 作用 |
|---|---|
| `app/agent/after_sale/creation.py` | 创建摘要、仓储结果、业务冲突与身份/版本校验 |
| `app/agent/after_sale/service.py` | 原子创建接口、稳定错误结果、幂等响应及事件 |
| `app/infrastructure/sql_after_sale_repository.py` | SQL 创建事务、唯一冲突回读、CAS 更新 |
| `app/agent/after_sale/repository.py` | JSON 同文档幂等账本、读写锁、版本和唯一校验 |
| `app/infrastructure/file_lock.py` | 稳定旁文件上的线程/进程互斥 |
| `app/agent/tools/registry.py` | 可信 action_id 到创建键的上下文注入 |
| `app/infrastructure/migrations/versions/20261023_0003_case_creation.py` | 重复数据预检、升级与降级 |
| `app/scripts/case_creation_smoke.py` | 可在 SQLite/PostgreSQL 运行的 50 请求探针 |
| `tests/test_case_creation.py` | 本期行为回归及并发、故障、迁移验证 |

可用于简历的已验证内容：以部分唯一索引和事务消除工单创建竞态；持久化业务
幂等键并拒绝异参复用；引入 version CAS 防止并发审批覆盖；用线程、多进程和
故障注入证明上述约束，并验证迁移对历史重复数据的保护。

创建幂等账本当前没有自动 TTL 清理，以免旧键失效后重试变成新请求。外部退款
exactly-once、Provider 查询对账和任务恢复仍是后续工作；本期不会自动重放第 23
期处于 executing/unknown 的 action。业务幂等提供恢复依据，不等同于自动恢复。
