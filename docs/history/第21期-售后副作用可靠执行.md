# 第 21 期：售后副作用可靠执行

> 历史归档：记录当时的设计、实现与验收范围，不代表当前运行状态。当前入口见 [文档导航](../README.md) 与 [验收状态](../evaluation/acceptance.md)。原始证据保持原版本，不追改历史测量结果。

本阶段把售后工单从“调用退款后再修改工单状态”升级为带持久化事务日志的可靠执行
流程。重复请求、短暂失败、进程中断和外部结果已生效等情况，都由确定性代码恢复，
不交给模型判断是否再次退款。

> 阶段状态：已完成；完成日期：2026-08-23；验收不访问真实或本地模型服务。

## 1. 设计目标

阶段 21 解决四个问题：

1. 工单进入 `processing` 后进程中断，系统无法判断是否应该重试；
2. 两个请求同时执行同一工单，可能重复调用退款适配器；
3. 外部退款已生效但本地工单未完成，重启后缺少收敛依据；
4. 重试耗尽和人工补偿没有独立状态、权限与审计入口。

新的权威执行路径为：

```text
execute_after_sale_case
  → 读取已批准工单
  → 生成稳定幂等键与请求摘要
  → AfterSaleOperationRepository 原子抢占执行租约
      ├─ claimed：调用退款适配器
      ├─ in_progress：拒绝重复执行
      ├─ replay：回放已持久化成功结果
      └─ exhausted：停止自动重试，转人工处理
  → 持久化操作结果
  → 收敛工单状态与审计日志
```

## 2. 操作模型与幂等约束

每个工单只有一个退款执行身份：

```text
idempotency_key = after_sale.execute:<case_id>
operation_id    = ASOP-<幂等键摘要>
request_hash    = SHA-256(case_id/order_id/reason/user_id/operation_type)
```

`request_hash` 防止同一幂等键被复用于不同参数。操作日志同时记录：

| 字段 | 作用 |
|---|---|
| `status` | `running / failed / succeeded / exhausted` |
| `attempt_count / max_attempts` | 限制自动执行次数 |
| `version` | 条件更新与并发冲突检测 |
| `lease_expires_at` | 判断运行中操作是否已经失去执行者 |
| `result / error` | 成功回放、失败诊断与恢复依据 |
| `compensation_status` | `not_required / pending / completed / failed` |

成功结果先写入操作日志，再更新工单。以后无论来自工具、API 还是恢复入口的重复请求，
都直接回放同一结果，不再次调用退款适配器。

## 3. JSON 与 SQL 原子抢占

`AfterSaleOperationRepository` 提供 `get / claim / save / list / list_recoverable`
统一协议。

JSON 后端使用同一路径共享的进程内锁、版本校验和临时文件原子替换，适合单进程教学、
测试和轻量开发；日志路径可通过 `AFTER_SALE_OPERATION_PATH` 配置，留空时与工单文件
保存在同一目录。SQL 后端使用：

- `idempotency_key` 主键和唯一 `operation_id`；
- 首次抢占的唯一键插入；
- `WHERE idempotency_key = ? AND version = ?` 条件更新；
- 唯一键竞争后的重新读取；
- 面向状态、用户、工单和补偿状态的查询索引。

因此，多线程或多进程同时提交同一工单时，只有一个执行者得到有效租约。其他请求返回
`in_progress` 或已完成结果。

## 4. 失败、恢复与外部结果收敛

一次执行失败后，操作进入 `failed`，工单回到 `approved`，下一次请求可以重新抢占。
达到 `AFTER_SALE_OPERATION_MAX_ATTEMPTS` 后，操作进入 `exhausted`，工单进入
`execution_failed`，系统不再自动调用退款适配器。

如果进程在 `running` 阶段中断，租约超过
`AFTER_SALE_OPERATION_LEASE_SECONDS` 后会出现在可恢复列表中。管理员恢复时沿用原
幂等键并增加尝试次数。

退款适配器必须接收并传递幂等键。当前 SQL 演示适配器会识别订单已有退款或
`refund_processing` 状态，并返回 `effect_applied=true`。这覆盖“外部操作成功、本地
操作日志尚未完成”的崩溃窗口：恢复执行不会创建第二笔退款，而是把操作日志和工单
收敛到 `succeeded / completed`。

## 5. 补偿状态与人工边界

已成功的副作用操作可以登记补偿流程：

```text
not_required → pending → completed
                       └→ failed → pending
```

补偿状态只能由具有 `after_sale:recover` 权限的管理员修改，所有变更同时写入工单
审计日志和 EventBus。这里的补偿是人工处理状态与证据记录，不会自动调用支付冲正或
其他真实外部接口。

## 6. API、管理页与独立脚本

普通用户只能查询自己的执行记录：

- `GET /v1/after-sales/{case_id}/operation`。

管理员入口：

- `GET /v1/admin/after-sales/operations`：查询操作历史；
- `GET /v1/admin/after-sales/operations/recoverable`：查询失败或租约过期操作；
- `POST /v1/admin/after-sales/{case_id}/recover`：恢复执行；
- `POST /v1/admin/after-sales/{case_id}/compensation`：登记补偿状态。

内置管理页展示操作状态、尝试次数和补偿状态，并提供恢复及补偿按钮。独立脚本新增：

```bash
python app/scripts/review_after_sale.py operations
python app/scripts/review_after_sale.py recover AS-XXXXXXXXXX \
  --reviewer customer-service-01
python app/scripts/review_after_sale.py compensate AS-XXXXXXXXXX \
  --status pending --reviewer customer-service-01 --note "需要冲正"
```

## 7. 事件与代码结构

操作抢占、执行中冲突、失败、重试耗尽、完成、成功回放和补偿变更分别发送
`after_sale.operation.*` 事件，继续复用现有 JSONL、指标、SSE、WebSocket 和测试
订阅器。

主要代码：

- `agent/after_sale/models.py`：操作、租约、重试和补偿状态；
- `agent/after_sale/operation_repository.py`：仓储协议、抢占纯函数及 JSON/内存实现；
- `infrastructure/sql_after_sale_operation_repository.py`：SQL 原子抢占与乐观锁；
- `infrastructure/database.py`：`after_sale_operations` 表和索引；
- `agent/after_sale/service.py`：执行、回放、恢复、耗尽与补偿状态机；
- `services/commerce.py`：向退款适配器传递幂等键；
- `api.py`、`web/admin.html`、`scripts/review_after_sale.py`：运维入口；
- `tests/test_side_effect_reliability.py`：阶段 21 纯离线回归。

## 9. 阶段边界与后续完成状态

阶段 21 只保证售后副作用执行协议，不把真实支付、仓储或供应商系统纳入本地事务。
生产适配器必须真正持久化和识别幂等键，数据库结构仍应通过 Alembic 等工具受控迁移。

阶段 22 已增加计划步骤超时、取消传播、资源配额，并将固定计划数据集纳入调度、
恢复与路由一致性质量门禁。真实支付、仓储和供应商系统仍属于部署环境联调边界。
