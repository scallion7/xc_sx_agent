# 第 2 期：多轮对话管理

> 历史归档：记录当时的设计、实现与验收范围，不代表当前运行状态。当前入口见 [文档导航](../README.md) 与 [验收状态](../evaluation/acceptance.md)。原始证据保持原版本，不追改历史测量结果。

讲之前叠个甲：现在模型能力越来越强，上下文窗口也越来越大，也许以后用不着做 summary 了，但至少目前的阶段对于长上下文、多工具调用的 Agent 是需要的



❓对于长上下文的 Agent，聊 50 轮，如果每轮都把完整 history 塞回去给 LLM，单轮输入会随轮数近似线性增长，累计 token 消耗通常接近二次增长；同时模型注意力被稀释到巨长的历史里，Agent 效果可能会越来越糟



这个问题最主流的解法叫 Summary



保留最近N轮原文，更早的交给LLM自己总结。消息压缩策略通常为上下文达到一定的token数，例如claude code通常为达到最大上下文窗口的70%左右自动压缩

在我们这个学习demo里就简单一点做，消息超过10条就触发一次压缩，留最近3条，其余压成一段摘要



而关键在于摘要不能写成"用户之前说了啥"的流水账，得是提取核心的内容：“用户身份、订单号/商品、核心诉求、客服已承诺的事、没回答的问题”

这五条是我针对电商客服这个具体业务场景编的"记忆骨架"，不一定全，但大概表达了这种意思，不管聊多久都不能丢。换个场景（比如医疗垂类、法律垂类），设计思路是通用的



❗️更关键的一个设计：累积式

踩过坑的应该懂，第一次压缩完，第二次触发时怎么办

如果只压最新的老对话、丢掉上次摘要，聊到第100轮，第10轮提过的订单号早就没了

正确做法是每次压缩把上次摘要也加进来

这形成的是会话内的滚动摘要：模型始终带着一份“不断被重写的档案”工作，关键事实随压随留。它解决长对话压缩，但不等同于第 7 期实现的跨会话长期 Memory
