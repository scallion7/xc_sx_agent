# 第 17 期：Plan-and-Execute 2.0 与确认恢复

> 历史归档：记录当时的设计、实现与验收范围，不代表当前运行状态。当前入口见 [文档导航](../README.md) 与 [验收状态](../evaluation/acceptance.md)。原始证据保持原版本，不追改历史测量结果。

本阶段在第 16 期结构化计划与工具参数契约的基础上，补齐跨步骤数据传递和副作用操作
的确定性恢复机制。用户确认只作用于当前计划中明确展示的待确认步骤，确认轮不重新
规划、不重复查询，也不能通过 ReAct 绕过原计划。

> 阶段状态：已完成；完成日期：2026-08-03；验收不访问真实或本地模型服务。

## 1. 前序步骤输出引用

后续步骤的参数支持引用已完成步骤的输出：

```text
${steps.<step_id>.output.<field_path>}
```

引用支持：

- 字典字段；
- 列表索引；
- 完整输出对象；
- 原始字符串、数字、布尔值、字典和列表类型。

引用步骤必须存在于当前计划，并且必须写入 `depends_on`。未知步骤、缺少显式依赖、
路径不存在或列表越界都会被确定性拒绝，不会调用目标工具。

## 2. 精确恢复待确认步骤

- 首次执行只自动调用只读工具；
- 副作用工具进入 `awaiting_confirmation`；
- 用户明确回复确认后，执行器恢复原计划；
- 已完成步骤直接复用，不重复调用；
- 只授权上轮明确列出的待确认步骤；
- 后续新增的副作用步骤仍需再次确认；
- 确认状态在副作用工具调用前被消费并持久化，避免进程退出后重复确认。

阶段 16 的确认轮原先会返回 ReAct。阶段 17 起，确认轮不再请求规划，也不再切换到
ReAct 执行副作用，而是恢复持久化计划中的精确步骤。

## 3. 计划状态随会话恢复

待确认的 `PlanExecutionResult` 会写入会话运行状态。Agent 或 API 请求重新创建实例后，
仍可恢复同一计划并继续确认流程。

该实现复用现有 JSON/SQL 会话载荷，不新增数据库表或迁移要求。计划中的已完成结果、
待确认步骤和依赖关系会一起恢复。

## 4. 旧计划自动取消

存在待确认计划时，如果用户发送新的非确认请求，系统会先取消旧计划，再处理新请求。
取消状态会立即写入会话，避免后续的“确认”误作用于已经失去上下文的操作。

## 5. 失败隔离与确定性降级

- 工具实现抛出的异常会转换为失败步骤，不会中断整个 Agent；
- 已失效的持久化计划不会回退到 ReAct，而是终止待确认操作；
- 工具执行后如果模型汇总失败，使用本地确定性摘要返回结果；
- 汇总失败不会重新调用已执行工具；
- 新增 `plan.resumed`、`plan.cancelled`、`plan.resume.failed` 和
  `plan.synthesis.fallback` 事件。

## 6. 代码结构

- `agent/strategies/executor.py`：计划校验、输出引用、恢复和工具执行；
- `agent/strategies/plan_execute.py`：模型规划、结果汇总和确认提示；
- `agent/chat.py`：待确认计划的会话生命周期；
- `agent/base.py`：通用运行状态的持久化扩展点。

外部仍通过 `app.agent.strategies` 导入公开接口，原有调用方式保持兼容。
