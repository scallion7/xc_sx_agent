# 可信执行与业务一致性

[文档中心](../README.md) · [当前验收](../evaluation/acceptance.md)

系统将模型建议、用户授权和业务执行分成独立步骤。模型传入 `user_confirmed=true` 不能替代真实确认；订单归属、证据有效性、风险规则和工单状态由服务端校验。网络错误也不能被解释为“业务未执行”。

## 提案与授权生命周期

统一工具执行层为写操作生成绑定用户、会话、工具、参数哈希、业务版本及有效期的 action。用户确认的是该 action 的具体内容；参数、风险规则、订单状态变化或人工修订可能使旧确认失效。领取执行时重新检查权限、所有权和业务快照。

普通提案只在内容及范围一致、未过期，且状态为 `pending`、`confirmed`、`executing`、`completed` 或 `unknown` 时复用。已经拒绝、失效或过期的提案不再阻塞用户重新申请：新申请生成新的 `pending` action，必须重新确认。旧 action 保持原状态，持有旧 ID 仍不能执行。结果未知的业务仍需按执行账本核对，提案去重不能替代业务幂等或对账。售后草稿的提案由自己的命令回执和修订管理，不依赖普通提案去重。

工单创建通过数据库唯一约束与创建回执控制并发，工单修订使用 CAS。HTTP 商务沙箱使用事务 Outbox 投递退款命令，Inbox 去重回执，对账任务查询供应商结果。普通外部适配器通过下述查单协议恢复。两条路径都沿用原业务键。

## 普通外部退款的查单协议

对接 `RefundProvider` 时，通过已批准工单执行退款。首次领取先持久化 `after_sale.execute:<case_id>`，随后调用一次 `submit_refund`。接口响应丢失、返回处理中或只带成功文案时，工单保持处理中。工具及 run 能识别业务结果中嵌套的供应商超时，保留待核对状态。旧兼容工具没有工单业务键时返回 `REFUND_CASE_REQUIRED`。

适配器把提交响应和 `get_refund(idempotency_key)` 的查询响应统一映射成以下字段。项目以工单记录校验业务键、归属及金额，并持久化供应商退款编号。接口类型见[退款回执契约](../../app/services/refund_contracts.py)。

| 回执字段 | 接入约定 |
|---|---|
| `idempotency_key`、`order_id`、`user_id` | 分别对应原业务键、订单号和工单用户 |
| `amount_cents`、`refund_id` | 以整数分表示的工单金额、供应商退款编号 |
| `status` | `processing` 表示继续查单。仅 `succeeded` 和 `failed` 表示供应商已确认的终态 |

管理员通过原工单的 `recover` 接口查原键。退款编号缺失、归属或金额不符、暂时查不到及供应商离线均保持待核对。external 模式下，升级前缺少供应商标识的成功、失败、耗尽和租约到期记录都需查原键，因为旧成功记录可能只代表已受理。若旧清理已移除操作行，工单中的执行历史仍可用于恢复原业务键并查单。SQL 清理保留 external 部署的旧操作账本，JSON 清理保护配置中的工单与操作文件。相关回归使用受控适配器模拟响应丢失、进程重启和并发查单。[外部退款恢复测试](../../tests/test_external_refund_recovery.py)

## 业务对账与 Agent run 结案

持久化 run 为模型和工具记录调用日志。写调用在领取 action 或分发业务前，先绑定 action ID、参数哈希和业务版本；本地执行路径带 `action-v1` 契约。发生崩溃或执行结果不明时，run 进入 `needs_reconciliation`，保留当前会话的阻塞状态。工具调用日志中的 `completed` 仅表示调用记录完成，不能单独证明退款或工单已经落定。

管理员拥有 `after_sale:recover` 权限后，先调用 `GET /v1/admin/runs/{run_id}/reconciliation` 读取当前版本和每个写调用的证据，再向 `POST /v1/admin/runs/{run_id}/resolve` 提交 `expected_version`、完整的 `call_id` / `evidence_hash` 集合及核对说明。服务器重新检查租户、用户、会话、工具、参数和业务版本，不能靠人工文字说明跳过缺失证据。

| 可核验情况 | 结案依据 |
|---|---|
| 新契约调用尚未绑定 action | `action-v1` 保证绑定发生在分发前，可证明未分发 |
| action 尚未领取或已拒绝、失效、过期 | 在锁内确认没有已领取的业务效果；结案时撤销仍待确认或已确认的授权 |
| 创建售后工单 | `action:<action_id>` 对应的持久化创建回执，以及同一用户、订单的工单 |
| 执行售后工单 | 普通外部适配器提供已关联且符合金额、身份和终态要求的回执。HTTP 沙箱的操作须结算，相关投递和对账队列全部 `sent`。旧的可重试 `failed` 仍须核实 |
| 确定未执行的失败 | 已完成 action 的结构化失败回执，错误码属于明确的参数、权限、过期、状态变化或执行前拒绝白名单，且没有已受理或已产生效果标记 |

处理会先锁定并验证所有写调用的证据，再按不同 action 更新状态；同一 action 出现在多个调用中也使用同一轮证据。action、业务操作和队列锁配合最终 run CAS，确保结案、`run.resolved` 事件与平台审计在同一事务提交。证据变化、部分缺失、重复 call ID、并发结案或审计写入失败都会拒绝或回滚。

结案后 run 为 `resolved`，撤销旧租约并递增 fence，会话可以接收新请求。它表示已核对并关闭原执行流程，不等于所有业务都成功，也不会自动续跑旧模型计划。旧调用日志若没有可绑定的 action 回执，或业务仍为 `pending` / `unknown`，保持阻断；当前没有为任意远端工具提供通用的人工强制成功入口。

## 保证与前提

| 机制 | 可以保证的范围 | 不自动保证的内容 |
|---|---|---|
| 活跃工单唯一约束 | 同一用户与订单满足约束的活跃工单不会并发重复落库 | 所有远端业务动作都只发生一次 |
| 幂等键与回执 | 同一业务请求可复用已提交结果 | 不同键表达同一业务意图时自动去重 |
| 租约 fencing | 旧 Worker 的本地过期提交被拒绝 | 已发往远端的请求自动撤销 |
| Outbox / Inbox | 本地事务与待发送意图一致、重复回执可去重 | 消息只投递一次、外部系统无条件精确执行一次 |
| 退款对账 | 结合供应商查单与幂等能力收敛最终状态 | 缺少查单或幂等能力时仍承诺无重复资金动作 |
| run 核对结案 | 依据当前持久化回执关闭阻塞任务，保留审计 | 将缺失回执、超时或普通成功文案视为业务证明 |
| 人工接管 | 所有权版本检查阻止旧任务登记新调用，旧回复不自动发送 | 撤销已经被供应商受理的命令 |

对外应表述为“在稳定业务键、数据库约束和供应商能力前提下实现幂等业务效果与可对账恢复”，避免无条件的端到端 exactly-once 承诺。
