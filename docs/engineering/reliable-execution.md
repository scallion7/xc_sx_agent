# 可信执行与业务一致性

系统将模型建议、用户授权和业务执行分成独立步骤。模型传入 `user_confirmed=true` 不能替代真实确认；订单归属、证据有效性、风险规则和工单状态由服务端校验。

## 从提案到结果

1. 统一工具执行层识别写操作，生成绑定用户、会话、参数哈希、业务快照和有效期的提案。
2. 用户确认特定提案；参数变更或人工修订后，旧确认不再有效。
3. 工单创建以数据库唯一约束和幂等记录控制并发，版本更新使用 CAS。
4. 异步任务使用租约和递增 fencing token，过期 Worker 无权提交新的本地最终状态。
5. 需要远端执行时，以事务 Outbox 保存命令，以 Inbox 去重回执；响应丢失时先按稳定业务键查询。
6. 对账确认最终结果，或转入 `needs_reconciliation` 等人工核对状态。

## 保证与前提

| 机制 | 可以保证的范围 | 不自动保证的内容 |
|---|---|---|
| 活跃工单唯一约束 | 同一用户与订单满足约束的活跃工单不会并发重复落库 | 所有远端业务动作都只发生一次 |
| 幂等键与回执 | 同一业务请求可复用已提交结果 | 不同键表达同一业务意图时自动去重 |
| 租约 fencing | 旧 Worker 的本地过期提交被拒绝 | 已发往远端的请求自动撤销 |
| Outbox/Inbox | 本地事务与待发送意图一致、重复回执可去重 | 消息只投递一次、外部系统无条件精确执行一次 |
| 退款对账 | 结合供应商查单与幂等能力收敛最终状态 | 供应商缺少查单/幂等能力时仍承诺无重复资金动作 |
| 人工接管 | 接管成功后阻止新的自动写动作，模型结果不自动回到客户历史 | 撤销已经被供应商受理的命令 |

因此，对外应表述为“在稳定业务键、数据库约束和供应商能力前提下实现幂等业务效果与可对账恢复”，避免无条件的端到端 exactly-once 承诺。
