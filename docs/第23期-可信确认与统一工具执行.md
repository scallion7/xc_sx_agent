# 第 23 期：可信确认与统一工具执行

本期解决一个具体问题：此前工具参数中的 `user_confirmed=true`、
`evidence_provided=true` 可以由模型生成，计划层的确认也不能自动保护 ReAct
路径。现在模型只能提出业务操作；应用依据用户的独立确认记录决定能否执行。

实现范围：单 Agent / Multi-Agent ReAct、Plan-and-Execute、手动业务操作 API，
以及现有三个写工具 `create_after_sale_case`、`execute_after_sale_case`、
`apply_refund`。创建工单与执行工单是两个独立动作，分别确认。

## 1. 可信边界与执行流程

```text
模型工具调用 / 计划步骤 / 手动 action execute
  → ToolManager → ToolExecutionService
  → 白名单 + 权限 + Pydantic 参数校验
  → 规范化参数 + 读取业务快照
  → ActionProposal（未确认时仅返回提案）
  → 真实用户确认（认证 API 或精确匹配的聊天确认）
  → 重新检查参数、业务版本和有效期
  → SQL 条件更新：confirmed → executing
  → 再读业务快照、检查截止时间 → ToolRegistry → 领域服务
  → 保存结果与状态 → 返回业务结果 + action
```

`ToolExecutionService` 处理公共边界；`AfterSaleService` 等领域服务继续负责
订单归属、工单状态、人工审批和 Provider 操作。旧管理员审核、恢复、补偿接口
保留原有鉴权和领域服务路径，本期没有把所有管理接口改成用户确认流程。

关键文件：

| 文件 | 职责 |
|---|---|
| `app/services/tool_execution.py` | 参数解析、权限、提案、确认消费、截止时间、错误及工具事件 |
| `app/services/actions.py` | SQL 提案/确认/证据账本、条件更新和结果持久化 |
| `app/schemas/actions.py` | 对外提案、证据记录模型 |
| `app/agent/tools/registry.py` | 工具契约与业务快照适配器，阻止无 action 上下文的直接写调用 |
| `app/agent/base.py` | 可信聊天确认、提案展示、重置撤销 |
| `app/agent/strategies/executor.py` | 计划提案、原 action 绑定恢复、取消及截止时间传播 |
| `app/web/actions.py` | 认证后的查询、确认、拒绝、执行及证据接口 |
| `tests/test_trusted_actions.py` | 离线行为回归与并发/迁移验证 |

模型不能提供 `actor`、权限或可信执行上下文。模型原始 JSON 在统一入口解析，
格式错误返回 `INVALID_ARGUMENT`，让 ReAct 得到可恢复的 Observation。
旧布尔参数为兼容仍保留，但在计算参数摘要前归零；只有执行入口可以根据账本
和已审核证据重新生成领域服务需要的布尔值。

未知远端 MCP 写工具返回 `REMOTE_TOOL_UNGOVERNED`。独立 MCP 教学服务没有
可信用户/会话认证，退款入口返回 `ACTION_SCOPE_REQUIRED`，不调用退款处理器。
主应用中的用户绑定业务工具始终使用本地适配器。

## 2. 数据模型与状态

| 记录 | 关键字段 | 约束 |
|---|---|---|
| `ActionProposal` / `action_proposals` | action_id、user_id、session_id、tool_name、arguments_json/hash、business_version、status、expires_at、result_json | 按用户和会话访问；参数规范化后 SHA-256；到期不能消费 |
| `action_confirmations` | action_id、actor、channel、arguments_hash、confirmed_at | action_id 主键；确认状态更新与记录插入同一事务 |
| `EvidenceRecord` / `evidence_records` | evidence_id、user_id、order_id、content/hash、status、reviewer、created_at | 使用时校验用户和订单；只有 verified 算已审核举证 |

业务版本是当前订单、相关工单状态及审批、有效风险规则、引用证据的内容摘要和
审核状态的组合哈希。参数、订单、审批、规则或证据审核变化，需要新的确认。
客户端不能修改提案参数；请求不同参数会产生不同的提案，旧提案不会授权新参数。
本期未自动撤回所有旧提案；存在多个待确认提案时必须逐项按 ID 操作。

```text
pending → confirmed → executing → completed
   │          │           └──────→ unknown
   └──────────┼──→ rejected / expired / invalidated
```

- `completed` 表示已经记录确定结果，结果可能是业务拒绝，需同时检查 `success`。
- 同一 action 的 SQL 条件更新只允许一个执行者消费确认；重复查询/执行已完成
  action 返回存储结果和 `idempotent_replay=true`，不再次调用工具。
- 进程在领取后崩溃会保留 `executing`；不确定错误记为 `unknown`。两种状态都
  禁止自动重放，避免在无法判定外部副作用时再次提交。
- 过期在确认/执行校验时落为 `expired`；待确认列表直接过滤过期记录。
- 会话重置、删除会撤销该会话未消费的 pending/confirmed；计划取消撤销已关联
  步骤的未消费确认。已经执行的业务不能通过删除会话回滚。
- 提案及确认始终使用 `DATABASE_URL` 指向的 SQL 库；即使会话使用 JSON 后端，
  确认记录仍可跨进程重启保存。备份 JSON 会话时也需备份确认数据库。

## 3. 用户如何确认

聊天确认只接受完整短语：`确认`、`确认执行`、`同意`、`同意执行`、`继续执行`
（允许尾部中文句号或感叹号）。只有当前用户、当前会话存在唯一未过期的待确认
提案时才能授权；“先不要申请”“我之前确认过”等自然语言不能直接产生确认。

服务器在最终回复中展示实际待确认操作的订单/工单、原因和操作 ID，覆盖模型
可能生成的“已经完成”描述。多提案时一句“确认”不会批量执行。

ReAct 的确认轮直接调用统一执行入口，不依赖模型再次决定参数。计划模式先记录
真实确认，再由原计划使用原 action_id 和原工具白名单恢复；仅把
`confirmed_step_ids` 标记为已确认不能绕过账本。API 已执行动作后恢复计划会读取
同一 action 的存储结果。

## 4. API 演示

默认演示认证使用 `.env.example` 中的 `X-API-Key`。`session_id` 是客户端会话名；
服务端负责绑定认证用户，不能在请求体指定他人的用户 ID。先在同一会话通过聊天
发起售后请求，得到 `action_id`，也可查询列表：

```bash
curl -H 'X-API-Key: dev-user-token' \
  http://127.0.0.1:8000/v1/sessions/demo/actions
```

核对返回的具体操作后，将响应中的 ID 和 `arguments_hash` 替换到以下占位符。
**confirm 仅记录确认，不执行业务；execute 才消费确认并调用工具。**

```bash
curl -X POST -H 'X-API-Key: dev-user-token' -H 'Content-Type: application/json' \
  http://127.0.0.1:8000/v1/actions/ACTION_ID/confirm \
  -d '{"session_id":"demo","arguments_hash":"REPLACE_WITH_64_HEX_HASH"}'

curl -X POST -H 'X-API-Key: dev-user-token' -H 'Content-Type: application/json' \
  http://127.0.0.1:8000/v1/actions/ACTION_ID/execute \
  -d '{"session_id":"demo"}'

curl -H 'X-API-Key: dev-user-token' \
  'http://127.0.0.1:8000/v1/actions/ACTION_ID?session_id=demo'
```

| 方法与路径 | 权限及语义 |
|---|---|
| GET `/v1/sessions/{session_id}/actions` | session:read；当前作用域未过期 pending 提案 |
| GET `/v1/actions/{action_id}?session_id=...` | session:read；状态及已存结果 |
| POST `/v1/actions/{action_id}/confirm` | chat:use；body 包含 session_id、arguments_hash |
| POST `/v1/actions/{action_id}/reject` | chat:use；body 包含 session_id；只能撤销未消费操作 |
| POST `/v1/actions/{action_id}/execute` | chat:use；body 包含 session_id；仍检查工具权限和配置 |
| POST `/v1/evidence` | chat:use；body 包含自己订单的 order_id、content |
| POST `/v1/admin/evidence/{evidence_id}/review` | after_sale:review；body 为 status: verified/rejected |

证据第一版接收文本说明；上传后为 `submitted`，用户自己提交不等于审核通过。
管理员审核后，将 `evidence_id` 作为创建工单的 `evidence_ids` 参数传入。未审核
证据不会被算为有效举证；引用他人的证据或其他订单证据直接拒绝。尚未实现文件
上传、病毒扫描、OCR 或证明材料真实性识别。

HTTP 参数错误遵循现有 API 错误结构；提案不可见返回 404，确认状态冲突返回
409。`execute` 返回工具业务结果，调用者不能只看 HTTP 200，还须检查
`success`、`error_code` 与 `action.status`。

工具路径发出 `tool.started/completed/failed`、`action.proposed/confirmed`；拒绝
与证据审核 API 发出 `action.rejected`、`evidence.reviewed`。确认主体、渠道、摘要
和时间保存在 SQL 确认表中，事件总线沿用已有 trace 与订阅器。

`ACTION_CONFIRMATION_TTL_SECONDS=900`，支持 1–86400 秒。确认 TTL 与计划 TTL
分别管理，不能用仍有效的计划延长过期业务确认。

```bash

python -m app.scripts.database_smoke
```

新增迁移 `20261023_0002`，前驱为 `20260823_0001`。旧基线迁移冻结已有表名范围，
避免导入最新 metadata 时提前创建本期表；新迁移显式创建三张表及 scope 索引。
支持旧版本升级、降级到旧版本再升级；降级会删除本期确认/证据数据，保留基线表。
正式环境继续设置 `DATABASE_AUTO_CREATE=false`，由 Alembic 管理 schema。

## 7. 能证明的能力与下一期边界

本期可演示：模型给出 `user_confirmed=true` 仍不创建工单；用户真实确认后执行；
重复执行返回相同结果；更换用户或修改业务条件后拒绝执行。它体现信任边界设计、
SQL 条件更新、状态机、契约校验、迁移兼容和故障测试，简历中可描述这些已实现能力。

本期保证的是同一 action 的确认一次性领取，不是全链路 exactly-once。以下仍是后续开发：

1. 不同 action 并发创建同一订单工单的数据库唯一约束与业务幂等，已在
   [第24期](第24期-工单并发唯一约束与业务幂等.md)实现；本页保留第 23 期验收记录。
2. Provider 幂等键、执行未知结果查询、对账和可审计恢复；本期不自动重放未知写操作。
3. 工具截止时间在调度前及写操作发出前检查，不能硬中断已经开始的 Python/外部调用。
   快照复核也不是跨数据库与外部服务的原子事务，最终一致性仍需 Provider 条件写入。
4. 审核证据不可变版本及完整历史；本期存储当前审核状态与 reviewer，并发变化靠快照复核发现。
5. 前端可点击确认卡片、文件证据、多提案交互以及真实模型与供应商联调。

运行时应用代码属于可信执行环境，不能把它与允许任意模型生成 Python 的沙箱混用。
`ToolExecutionContext.action_id` 由应用填充，不是提供给模型的工具参数。
