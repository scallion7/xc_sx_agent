# 第 11 期：架构演进与应用工厂

## 目标

本阶段不重写已有业务能力，而是先建立可以持续替换旧架构的稳定接缝：

1. 单 Agent 与 Multi-Agent 共享会话运行时；
2. 配置和模型客户端可以按实例注入；
3. 所有应用入口通过统一工厂创建 Agent；
4. 评估环境不修改全局配置；
5. 保持 `EcomAgent()`、`MultiAgentOrchestrator()` 和现有 CLI 兼容。

## 当前分层

```text
main.py / evaluation / future API
              │
              ▼
      app.bootstrap.create_agent
              │
       ┌──────┴──────┐
       ▼             ▼
   EcomAgent   MultiAgentOrchestrator
       └──────┬──────┘
              ▼
    BaseConversationAgent
      ├─ session persistence
      ├─ memory and skills
      ├─ structured response
      └─ history compression
```

`BaseConversationAgent` 只管理公共生命周期，不决定路由或工具调用策略。
因此后续替换 ReAct 循环、路由器或模型 SDK 时，不需要再次复制会话逻辑。

## 统一创建入口

```python
from app.bootstrap import create_agent

agent = create_agent(mode="single")
agent = create_agent(mode="multi")
agent = create_agent(mode="auto")  # 跟随 MULTI_AGENT_ENABLED
```

测试或私有部署可注入配置和兼容 OpenAI 接口的客户端：

```python
agent = create_agent(
    mode="single",
    config=runtime_config,
    client=model_gateway,
)
```

## 兼容策略

- 原有构造方式继续有效；
- `EcomAgent.messages` 继续提供完整模型上下文；
- `ToolManager` 未传 `after_sale_enabled` 时仍读取旧的全局配置；
- Memory 和 Skill 的模块级工具注册暂时保留为迁移兼容层。

## 后续迭代路线

### 阶段 12：实例级工具注册

用 `ToolRegistry` 实例替代模块级 `_TOOL_MAP` 和 memory/skill setter，彻底解决
多个 Agent 实例互相覆盖依赖的问题。

### 阶段 13：模型网关

定义模型调用协议和统一重试、超时、限流、可观测性策略，把 OpenAI SDK 从业务
Agent 中移到基础设施层。

### 阶段 14：事件与可观测性

用事件接口替换核心代码中的 `print`，由 CLI、WebSocket、日志和评估采集器分别订阅，
并统一记录 trace id、tool latency、token usage 和失败原因。

### 阶段 15：服务化与持久化

增加 API 层、会话仓储接口和数据库实现；将当前 JSON 仓储保留为本地开发适配器，
业务服务只依赖仓储协议。
